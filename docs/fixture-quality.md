# Fixture and harness assurance

The PQ fixtures now have classical controls generated from the **same XML template**, in addition to the existing 24 classical XML signatures. These checks reduce the risk that a PQ failure is caused by the shared fixture format or verification harness; they do not prove every future failure is in the cryptographic implementation.

| Check | Evidence |
| --- | --- |
| XML structure and encoding | All 38 extended fixtures (30 PQ, 8 EdDSA), 25 stored libxmlsec reverse signatures, and 3 classical controls validate against the vendored W3C XMLDSIG core schema plus local envelope and draft SignatureContext schemas. |
| Same XML profile | All 38 extended fixtures match the classical control's serialized structure after masking only the algorithm URI, context element, and signature value. Payload, reference, transform, digest, namespace declarations, and canonicalization method remain identical. Exported canonical SignedInfo bytes are checked against fresh canonicalization. |
| Context-bearing classical control | All 30 PQ fixtures also match an Ed25519ph fixture with the same context, masking only the algorithm URI and signature value. Context elements and their encoding remain in this comparison. |
| Released XML library checks | RSA-SHA256 (PKCS#1 v1.5), ECDSA-P256-SHA256, and RSA-PSS-SHA256 controls verify in SignXML 5.3.1 and python-xmlsec 1.3.18 / libxmlsec 1.3.13. Both libraries reject modified payloads and signature values. |
| Same local and native harness | All three controls pass the extended-fixture adapter and explicit OpenSSL primitive checks. The pinned development libxmlsec build verifies and re-signs each control through the same `exercise()` path used for PQ. Reverse signatures verify through the local adapter and PyCryptodome. |
| Failure localization | Mutations prove that bad references, wrong algorithm URIs, payload digest mismatches, duplicate contexts, and application-context mismatches fail before the primitive verifier is called. A modified signature reaches the primitive verifier and fails there. Schema tests reject invalid base64, oversized contexts, and missing digests. |

SignXML receives a KeyInfo generated for the control key and added outside SignedInfo. The actual fixture signature, payload, and SignedInfo are not re-signed or replaced; a canonical-byte assertion checks that adding KeyInfo leaves SignedInfo unchanged. The native CLI similarly receives only a KeyName outside SignedInfo.

The schemas are offline inputs: the W3C file is preserved unchanged, with its source URL and SHA-256 in `schemas/provenance.json`. The envelope schema describes this test profile; the context schema implements the draft's base64Binary and 255-byte bound. XSD validation cannot establish algorithm support or cryptographic correctness. Semantic context checks remain necessary, including duplicate rejection and application policy.

## Interpreting a PQ failure

1. Parse and validate the XML; check the fixed profile and algorithm URI.
2. Check implementation capability. An unregistered algorithm is unsupported, not a bad signature.
3. Resolve the payload reference, canonicalize it, and check its digest.
4. Recompute canonical SignedInfo and compare with the exported bytes.
5. Check context policy, key selection, signature encoding, and backend configuration.
6. Verify the signature bytes using independent crypto implementations.

The adapter exposes `FixtureStructureError`, `ContextPolicyError`, `ReferenceDigestError`, and `SignatureVerificationError` for these tested failure classes. Malformed XML/base64 may still raise parser/decoder exceptions. A signature verification failure can arise from an incorrect key, context, encoding, or algorithm binding; it does not by itself establish a bug in the underlying crypto algorithm.

Existing native PQ results remain 18 interoperable cases and 12 unsupported SLH-DSA-SHAKE cases in the pinned development build. The separate Ed448 nonempty-context case is a known expected failure. See [native XML interoperability](native-xml.md) for versions, scope, and limitations. All 30 PQ fixtures pass schema and shared-profile checks, including the 12 without native XML-library support.

These controls establish evidence for the current one-payload, same-document reference, exclusive-canonicalization, SHA-256 fixture profile. They do not claim arbitrary XMLDSIG transform, certificate, or application-security coverage.

Run the focused checks with:

```sh
uv run pytest -q tests/test_harness_controls.py
```

Regenerate only the three classical controls with `uv run python -m xmlsec_vectors.harness_controls`. The existing PQ fixtures are not regenerated by this command. Full environment and suite results are recorded in [verification.json](verification.json).

The later [PQ release checks](pq-release-readiness.md) extend this baseline with fully signed context boundaries, XML base64 whitespace handling, prehash/key/length negatives, and a mandatory native release gate.
